Accepted architecture decision · EMB-1359

Chain-aware canonical token identity

Token identity comparison follows the address semantics of its chain id, dispatched by one pure, conservative classifier owned by @emberai/onchain-actions-contracts/core, instead of one unconditional lowercase rule. The one canonical evm domain representation is EIP-55 — never lowercase.

Context

The contracts package's private canonicalTokenKey lowercased every token address before comparing or keying it. That is correct for EVM equivalence, but Solana Base58 addresses are case-sensitive: two distinct, valid Solana public keys differing only in case were treated as duplicates in the token-market request and rejected as an ordering mismatch in the envelope.

The public TokenIdentifier.chainId field is an arbitrary non-empty string, not a self-describing chain identifier. Current EVM callers use legacy decimal Ember chain ids such as 42161; an existing internal Solana normalization utility uses the legacy literal solana. The address string alone cannot reliably determine its own family, so the family must be derived from chainId.

An initial correction chose lowercase as the canonical evm representation. Human Review rejected that choice: the system had accumulated repeated identity bugs precisely because equality, storage, provider matching, and public serialization used different case conventions for the same address. A public EIP-55 form plus a second, internal lowercase-keyed convention would have reintroduced that exact class of bug inside this Module. EIP-55 — not lowercase — is the one canonical evm domain representation after ingress.

Decision

One pure, deep CanonicalTokenIdentity Module in ./core owns identity validation, normalization, keying, and equality for every consumer: token-market request uniqueness, envelope result-order checks, and the TokenPriceReader host capability all delegate to it rather than reimplementing string policy.

Chain-family dispatch is a single conservative classifier, not a chain registry:

chainId shapeFamily
Legacy decimal Ember chain id (e.g. 42161)evm — case-insensitive; canonicalizes to the deterministic EIP-55 checksum form
Legacy solana literalsolana — case-sensitive
Self-describing CAIP-2 eip155:*evm, derived from the namespace
Self-describing CAIP-2 solana:*solana, derived from the namespace
Anything elseopaque — exact-case, never silently lowercased

An evm address is validated and canonicalized, not merely case-folded: CanonicalTokenIdentifierV1Schema requires a full 0x-prefixed 20-byte hexadecimal address, accepts either legacy all-lowercase input or an already-checksummed EIP-55 address, rejects an invalid mixed-case checksum outright, and always emits the deterministic EIP-55 checksum form. There is exactly one canonical evm representation behind this Interface — EIP-55 — used identically by normalization, canonical keying, equality, token-market request/envelope validation, and the TokenPriceReader Interface; no second, lowercase-keyed convention exists anywhere in this Module. viem's isAddress/getAddress are used internally as the evm family-specific codec: isAddress(address, { strict: true }) is what makes an invalid mixed-case checksum a hard validation failure (getAddress alone would silently re-checksum from the lowercase form instead of rejecting a bad checksum).

Lowercase remains valid only as ingress a caller may submit for a legacy all-lowercase address; it is never canonical output. A provider's documented wire Interface may still require lowercase on the wire — that projection stays local to the provider Adapter and is normalized back to the canonical EIP-55 representation before crossing the contracts Seam. Contracts, caches, persistence, evidence, and public responses only ever carry the canonical EIP-55 form. This includes graph persistence and graph projections by name: canonical graph properties, keys/indexes, reconciliation evidence, and reads all use EIP-55, not a lowercase-keyed convention. A frozen legacy graph property may remain lowercase only as a reversible migration artifact — never as a second canonical authority — and only until it is backfilled. Dual-projection/backfill of existing lowercase graph data onto the EIP-55 representation is implementation work this ADR does not perform; it is owned by EMB-1364, tracked as this ADR's open consequence below.

The classifier is pure and synchronous: it never queries Memgraph or another live registry, and its absence never invalidates an otherwise structurally valid token identity.

Four implementation invariants keep this decision precise:

  • CAIP-2 matching enforces the full CAIP-2 grammar, not only the namespace: the namespace is syntactically lowercase-only, not case-folded — EIP155:* and SOLANA:* are not valid CAIP-2 identifiers — and the reference must match [-_a-zA-Z0-9]{1,32}, so a reference containing a colon, whitespace, or more than 32 characters is likewise not valid CAIP-2 syntax. Either defect remains opaque exact-case rather than receiving evm/solana semantics.
  • canonicalTokenIdentityKey encodes the (chainId, address) pair with an unambiguous tuple encoding (not delimiter concatenation), because both a V1 chain id and a CAIP-2 chain id may themselves contain : — e.g. (eip155:1, 0xab) and (eip155, 1:0xab) would otherwise collide.
  • Every function in the Interface — including classifyTokenChainFamily itself — validates its chainId/address input through the same non-empty/trimmed invariant before dispatching on it, so no public entry point can be called directly to bypass that invariant.
  • CanonicalTokenIdentifierV1Schema is the single validation point for the evm address-format/checksum invariant: it runs as a schema transform, so every public identity operation — direct schema parse or the normalizeCanonicalTokenIdentifier/canonicalTokenIdentityKey/tokenIdentitiesAreEquivalent functions, which all delegate to it — normalizes identically, and no caller can reach a canonical key by constructing a parsed value that bypasses the schema.
  • CanonicalTokenIdentifierV1 is a branded (nominal), not structural, type. A plain { chainId, address } object literal — however well-formed — does not satisfy it; the compiler rejects that assignment. This is what makes the TokenPriceReader Interface's readTokenPrices(tokenUids: readonly CanonicalTokenIdentifierV1[]) parameter unforgeable: a caller cannot hand it raw, unvalidated input merely because the fields line up, and must instead route it through CanonicalTokenIdentifierV1Schema or normalizeCanonicalTokenIdentifier first.

Trade-offs

AlternativeRejected because
Infer the address family from the address shapeThe existing private normalizeToken.ts utility did this and it does not generalize; chainId semantics must be the authority, not the address string.
Look up chain type from a live chain registry (e.g. Memgraph)The contracts package must stay deterministic and usable without database availability; registry absence must never invalidate a structurally valid token.
Enumerate every supported chain id individuallyUnbounded maintenance surface for a V1 correction; the CAIP-2 namespace and two legacy conventions already cover the real cases without a table.
Let each plugin/endpoint normalize identity itselfReintroduces the original bug's root cause: duplicated, drifting string policy instead of one authority.
Fail closed (reject) on an unknown chain family instead of preserving exact caseThe operator refinement explicitly chose preserve-exact-case over rejection for V1; failing closed would reject structurally valid, provider-supported tokens on opaque chains that have no other current defect.
Canonicalize evm addresses to lowercase, with EIP-55 only as a public display formHuman Review rejected this: it recreates the exact bug class this ADR exists to close — equality, storage, provider matching, and public serialization drifting across two case conventions for the same address. One representation, enforced at ingress, has no such drift surface.
Accept only already-checksummed EIP-55 input and reject lowercaseWould break the legacy all-lowercase convention still in use by current callers with no compatibility path; accepting lowercase ingress while emitting EIP-55 canonical output covers both without weakening the checksum invariant on output.

Consequences

  • Case-distinct valid Solana addresses are always distinct identities; identical Solana addresses are always equal.
  • An opaque/unsupported chain id never has its address silently lowercased; extending semantics for a future opaque family requires extending this one classifier or first making chainId self-describing.
  • No plugin, endpoint, or downstream consumer may implement its own address-case normalization; all of them call the shared Interface.
  • A lowercase and an EIP-55-checksummed spelling of the same evm address are the same canonical identity: submitting both in one token-market request is a true duplicate and is rejected, exactly like submitting the same address twice.
  • A provider that requires lowercase on its own wire format keeps that projection entirely inside its Adapter; the canonical EIP-55 form is what crosses the contracts Seam, and no lowercase-keyed convention may re-enter contracts, caches, persistence, evidence, or public responses — including graph persistence: canonical graph properties, keys/indexes, reconciliation evidence, and reads all use EIP-55.
  • An existing frozen lowercase graph property is tolerated only as a reversible migration artifact, never as canonical authority; migrating it to a dual EIP-55 projection with backfill is out of this contracts-package correction's scope and is owned by EMB-1364.
  • A future migration from legacy chain ids to CAIP-2 is a separate compatibility decision and is not required by this correction.
