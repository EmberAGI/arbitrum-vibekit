Domain contract · EMB-1145

Onchain-action contracts and external data evidence

A dependency-light contract kernel owns the neutral onchain-action schemas, while every externally sourced value carries enough evidence for a consumer to decide whether it is current, partial, stale, or unavailable.

Public contract kernel dependency direction

The new package factors the neutral contract kernel out of the public registry package.

It is a dependency-light Module below registry and server implementations, not a replacement for either implementation Module.

Domain concepts

Snapshot

A versioned wire-format observation set with stable ID, quote currency, completeness, and creation context.

Provenance

The provider, capability, canonical subject, and source class that produced a field or item.

Freshness

Observation, receipt, expiry, refresh, and retry timing with an explicit timestamp source.

Completeness

Whether current values cover every requested subject, some requested subjects, or none. Item states independently explain stale, rate-limited, not-found, and unavailable outcomes.

Contract kernel

Neutral token, chain, transaction, plugin, action, query, lifecycle, plugin-host capability, endpoint, and evidence schemas shared by registry implementations and service consumers.

Canonical token identity

The chain-aware equivalence and keying rule for a token identifier, derived from its chain id's address family rather than its literal string casing.

These terms separate public contract ownership from registry and server behavior.

Rules and invariants

  • Every item validates as exactly one discriminated result state.
  • A current available result contains its value; an unavailable result cannot pretend to contain a current value.
  • A stale last-known value may be preserved only as evidence and retains its original observation time.
  • Receipt time never rewrites or extends provider observation time.
  • When provider observation time is absent, the fallback timestamp and its source are explicit.
  • Batch completeness is derived from item results and cannot hide a failed item.
  • Public warnings use stable safe codes; raw diagnostics and credentials never enter the contract.
  • A public plugin may depend on neutral host capabilities from ./plugins, but never on a concrete server service, container, HTTP client, registry runtime, or provider implementation.
  • Breaking semantic changes require a new contract version.
  • Wire properties use snake_case; timestamps are RFC 3339 UTC strings and decimal quantities are strings.
  • V1 provenance contains no cryptographic source digest or canonical-JSON hashing contract; consumers have no approved use case that requires one.
  • Token identity comparison follows the address family of its chain id, derived by ./core's canonical token identity Interface. It is never inferred from address shape and never unconditionally lowercased; an unknown or unsupported chain family always compares exact-case.

Result-state map

Available

Current value plus complete freshness and provenance evidence.

Stale

Optional last-known value remains evidence-only after freshUntil.

Rate limited

No fabricated current value; retry guidance may be supplied.

Not found / unavailable

The subject was unsupported, absent, invalid, or could not be observed.

Edge cases

  • A partial batch contains healthy and failed item results under one partial envelope.
  • Clock order and duration invariants reject impossible timing such as fresh_until < observed_at, received_at < observed_at, or refresh_after > fresh_until.
  • A cached value keeps its original provider observation time across later HTTP receipts.
  • Aggregated records may attach provenance per field when one item-level provider would be misleading.
  • Structurally invalid requests fail at the consuming HTTP or module interface. A valid subject whose provider payload is malformed returns an item-level unavailable result with a safe provider_payload_invalid code.
  • Envelope completeness is complete when every item is available, partial when some are available, and unavailable when none are currently usable.

Constraints

  • The package is lightweight and has no Aave, protocol SDK, network client, cache, or server dependency.
  • Zod schemas are the runtime validation authority and exported TypeScript types are inferred from them.
  • V1 uses a Zod 3 peer dependency so the registry and server share one compatible runtime schema instance.
  • The contract describes evidence rather than product-specific authorization policy.
  • The package exposes stable ./core, ./plugins, ./endpoints, and ./external-data entrypoints; consumers do not import package internals.
  • New consumers import contract entrypoints directly. The registry depends on the contracts package and temporarily re-exports only the neutral symbols it already exported so existing consumers remain source-compatible. It does not become the gateway for new evidence contracts.
  • Each moved schema or interface has one implementation source in the contracts package; the registry contains no duplicate definitions.
  • New plugin and host code imports TokenPriceReader directly from @emberai/onchain-actions-contracts/plugins. Because it is a new symbol, the registry does not become its compatibility gateway.
  • EMB-1144 imports token-market request/value/snapshot schemas directly from @emberai/onchain-actions-contracts/endpoints. The private server and registry do not duplicate or re-export those new contracts.
  • The package follows the repository's existing 0.0.0 semantic-release source version, public npm provenance, stable main channel, and prerelease next channel.

Non-goals

  • No provider fetching, retry, cache, or rate-limit implementation.
  • No registry runtime, registry configuration, or plugin discovery lifecycle redesign; EMB-1148 owns discovery work.
  • No Aave or other bundled protocol implementation moves into the contracts package.
  • No TokenPriceReader implementation, provider selection, price cache, HTTP client, or fallback policy lives in contracts; EMB-1144 supplies the private server implementation.
  • No wallet aggregation implementation; EMB-1146 consumes this contract.
  • No repository-wide migration of existing onchain-actions imports. That cross-repository adoption is separate linked work; new work such as EMB-1144 imports the external-data entrypoint directly.
  • No replacement or redesign of the private typescript/lib/ember-api MCP client or its broad DeFi request/response schemas. That client may consume the evidence package later through an explicit migration.
