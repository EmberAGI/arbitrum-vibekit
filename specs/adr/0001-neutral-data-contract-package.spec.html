Accepted architecture decision · EMB-1145

Neutral data-contract package

Public evidence schemas live below both the plugin registry and the server, not inside either implementation.

Context

The registry package already owns endpoint schemas but also bundles protocol implementations and Aave dependencies.

The server must share exactly the same validated DTOs without depending on plugin implementations.

EmberAGI/arbitrum-vibekit is the public repository that already owns public plugin contracts and npm release automation. EmberAGI/onchain-actions is a private server repository and is one consumer of the contract.

Decision

@emberai/onchain-actions-registry

Plugin interfaces and public plugin discovery.

←
@emberai/onchain-actions-contracts

Versioned Zod evidence schemas only.

→
onchain-actions

Provider orchestration and HTTP/MCP delivery.

The contracts package is imported directly by each consumer, uses a Zod 3 peer dependency, and owns the generic evidence schema factories. The registry does not re-export the package.

Trade-offs

AlternativeRejected because
Keep schemas only in the registry packageGeneric consumers inherit protocol implementation dependencies and ownership ambiguity.
Define schemas only in the serverPlugin/query authors lose the public source of truth and drift becomes likely.
Duplicate DTOsCompile-time similarity cannot enforce runtime semantic compatibility.
Re-export contracts through the registryReintroduces the dependency direction this package exists to remove and makes a protocol-heavy package the compatibility gateway.
Use Zod 4 for V1The registry and server currently consume Zod 3 schemas, including OpenAPI generation; a second incompatible schema runtime would break the shared seam.

Consequences

  • The contracts package must remain dependency-light and side-effect free.
  • The registry and server publish migrations against a shared versioned seam.
  • Provider implementations, cache behavior, and product authorization remain outside the package.
  • The existing private ember-api MCP client remains a separate consumer-facing Module; this decision neither replaces it nor migrates its broad endpoint schemas.
  • The existing multi-package release detector, dry-run validation, build/test steps, and OIDC publisher configuration must include the new package.
  • An operator must register the new npm package's trusted publisher for EmberAGI/arbitrum-vibekit, workflow release.yml, and the npm publish action before first release.
