Accepted architecture decision · EMB-1145

Neutral onchain-action contract kernel

Public core, plugin, endpoint, and evidence contracts live below both the plugin registry and the server, not inside either implementation.

Context

The registry package already owns neutral token, chain, transaction, plugin, action, query, lifecycle, and endpoint schemas but also bundles registry runtime, protocol implementations, and Aave dependencies.

The server imports the registry from 97 source and test files, frequently only to obtain these shared schemas and interfaces. It must share exactly the same validated contracts without depending on registry or plugin implementations.

EmberAGI/arbitrum-vibekit is the public repository that already owns public plugin contracts and npm release automation. EmberAGI/onchain-actions is a private server repository and is one consumer of the contract.

Decision

@emberai/onchain-actions-registry

Registry runtime, discovery, and bundled plugin implementations.

→
@emberai/onchain-actions-contracts

Neutral core, plugin, endpoint, and evidence schemas.

←
onchain-actions

Provider orchestration and HTTP/MCP delivery.

The contracts package uses a Zod 3 peer dependency and exposes stable ./core, ./plugins, ./endpoints, and ./evidence entrypoints. Neutral definitions move from the registry into those entrypoints and have one source of truth. The registry imports them and temporarily re-exports only its existing symbols for source compatibility; it does not re-export new evidence contracts. New consumers import the contracts package directly.

Trade-offs

AlternativeRejected because
Keep schemas only in the registry packageGeneric consumers inherit protocol implementation dependencies and ownership ambiguity.
Define schemas only in the serverPlugin/query authors lose the public source of truth and drift becomes likely.
Duplicate DTOsCompile-time similarity cannot enforce runtime semantic compatibility.
Keep the registry as the permanent contract gatewayRetains the dependency direction this package exists to remove. Compatibility re-exports are a migration bridge, not the preferred import surface.
Move every registry concern into contractsRegistry runtime, configuration, discovery, and protocol implementations are behavior rather than neutral contracts and would recreate the same coupling under a new name.
Use Zod 4 for V1The registry and server currently consume Zod 3 schemas, including OpenAPI generation; a second incompatible schema runtime would break the shared seam.

Consequences

  • The contracts package must remain dependency-light and side-effect free.
  • The registry depends on contracts and keeps its current public API source-compatible through tested re-exports; moved definitions are not duplicated.
  • New server work imports the appropriate contracts entrypoint directly. Repository-wide migration of the server's existing registry imports is separate linked work.
  • Provider implementations, cache behavior, and product authorization remain outside the package.
  • The existing private ember-api MCP client remains a separate consumer-facing Module; this decision neither replaces it nor migrates its broad endpoint schemas.
  • The existing multi-package release detector, dry-run validation, build/test steps, and OIDC publisher configuration must include the new package.
  • An operator must register the new npm package's trusted publisher for EmberAGI/arbitrum-vibekit, workflow release.yml, and the npm publish action before first release.
