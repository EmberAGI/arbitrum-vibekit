Domain contract · EMB-1145

External data evidence

Every externally sourced value carries enough evidence for a consumer to decide whether it is current, partial, stale, or unavailable.

Intended behavior

Provider payload

Untrusted value and timing metadata.

→
Adapter validation

Normalize identity, value, time, and provenance.

→
Item result

One valid discriminated state.

→
Snapshot envelope

Stable identity and batch completeness.

Domain concepts

Snapshot

A versioned wire-format observation set with stable ID, quote currency, completeness, and creation context.

Provenance

The provider, capability, asset identity, and optional safe source artifact that produced a field or item.

Freshness

Observation, receipt, expiry, refresh, and retry timing with an explicit timestamp source.

Completeness

Whether current values cover every requested subject, some requested subjects, or none. Item states independently explain stale, rate-limited, not-found, and unavailable outcomes.

Rules and invariants

  • Every item validates as exactly one discriminated result state.
  • A current available result contains its value; an unavailable result cannot pretend to contain a current value.
  • A stale last-known value may be preserved only as evidence and retains its original observation time.
  • Receipt time never rewrites or extends provider observation time.
  • When provider observation time is absent, the fallback timestamp and its source are explicit.
  • Batch completeness is derived from item results and cannot hide a failed item.
  • Public warnings use stable safe codes; raw diagnostics and credentials never enter the contract.
  • Breaking semantic changes require a new contract version.
  • Wire properties use snake_case; timestamps are RFC 3339 UTC strings and decimal quantities are strings.
  • A source digest is sha256:<lowercase hex> over the validated public provider observation after deterministic JSON key ordering; secrets and internal diagnostics are excluded.

Result-state map

Available

Current value plus complete freshness and provenance evidence.

Stale

Optional last-known value remains evidence-only after freshUntil.

Rate limited

No fabricated current value; retry guidance may be supplied.

Not found / unavailable

The subject was unsupported, absent, invalid, or could not be observed.

Edge cases

  • A partial batch contains healthy and failed item results under one partial envelope.
  • Clock order and duration invariants reject impossible timing such as fresh_until < observed_at, received_at < observed_at, or refresh_after > fresh_until.
  • A cached value keeps its original provider observation time across later HTTP receipts.
  • Aggregated records may attach provenance per field when one item-level provider would be misleading.
  • Structurally invalid requests fail at the consuming HTTP or module interface. A valid subject whose provider payload is malformed returns an item-level unavailable result with a safe provider_payload_invalid code.
  • Envelope completeness is complete when every item is available, partial when some are available, and unavailable when none are currently usable.

Constraints

  • The package is lightweight and has no Aave, protocol SDK, network client, cache, or server dependency.
  • Zod schemas are the runtime validation authority and exported TypeScript types are inferred from them.
  • V1 uses a Zod 3 peer dependency so the registry and server share one compatible runtime schema instance.
  • The contract describes evidence rather than product-specific authorization policy.
  • Consumers import the contracts package directly. The registry does not re-export it, and existing registry exports remain unchanged.
  • The package follows the repository's existing 0.0.0 semantic-release source version, public npm provenance, stable main channel, and prerelease next channel.

Non-goals

  • No provider fetching, retry, cache, or rate-limit implementation.
  • No plugin discovery lifecycle redesign; EMB-1148 owns that work.
  • No wallet aggregation implementation; EMB-1146 consumes this contract.
  • No transaction or action authorization types.
